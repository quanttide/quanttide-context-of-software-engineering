我们放弃了用了 10 年的 Python，然后转向了多语言的最新方案。

首先是服务端，我们一开始用 Django 转 FastAPI，后来整体放弃了 Python 转向了 Go。

一个直接的好处就是 Go 可以直接二进制上线，不需要容器化了，像部署 FasS 就非常方便。

我们在客户端选型上尽可能地避开了 JavaScript。如果实在要用的话，就用 TypeScript+React。

目前，我们这个 APP 主要使用的是 Flutter，小程序主要使用的是 Taro。官网主要使用的是 React。

尽可能避免 Python 和 JavaScript 的主要原因是，我们发现它们很容易被 AI 乱搞，在生产环境之中遭到破坏。所以，我们优先选择可以编译的语言，以及以编译的二进制包的形式发布。

另外一方面，国内容器发布的基础设施生态比较差。由于各种各样的原因，镜像站被封，各大云厂商提供的支持也比较贵和糟糕。所以相比之下，使用 FaaS 发布或者是直接上虚拟机都会更好一点。

还有一条备选方案是：客户端使用 React Native，后端也全部使用 TypeScript，形成使用 TypeScript 的全栈。这个是偏前端的开发者比较喜欢的一种范式

我们没有选择这个作为主要方案，有两方面原因：

一方面，历史上我们主要使用 Flutter 形成了习惯，就没有再往 React Native 迁移，也没有使用 TypeScript 或 JavaScript 写服务端的习惯。
另一方面，从写服务端的话，Go 语言总体来讲优势会更大一点，特别是对于高并发的应用，优势会更大一点。对于我们的品类来说的话 Go 和 Rust 是最优的，因为云原生的 SaaS、PaaS 或者是 infra，前者一般是 Go，后者一般是 Rust。

另外一个就是一些直觉上偏好感觉的问题：会觉得用一种语言去写不是很放心，但是多语言写就会带来多语言的负担。

特别是在让多语言的数据模型接口保持一致的时候，需要去平行地列举多个工具库，这会在前期开发带来不小的负担。

好处呢是后期在复用的时候，不同语言框架的复用会比较方便。这个好处，一时半会还看不出来。

这个选型很可能也不是终局的选型。因为在一些应用需要分离数据面和控制面时，控制面可能需要继续使用 Go，而数据面可能需要考虑使用 Rust，甚至根据业务需求采取其他的计算引擎。
