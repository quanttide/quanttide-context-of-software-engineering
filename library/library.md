Pi Agent 的核心循环是一个遵循 ReAct (Reasoning + Acting) 模式的**事件驱动、无限循环**的执行引擎，它持续协调大模型 (LLM) 的推理与工具的执行，直到任务完成。其核心可以概括为：
```mermaid
flowchart LR
    A[用户输入<br>注入上下文] —> B[调用 LLM<br>推理与决策]
    B —> C{输出判断}
    C — 包含工具调用 —> D[解析并执行工具]
    D —> E[结果注入上下文<br>作为 Observation]
    E —> B
    C — 纯文本或<br>声明结束 —> F[生成最终回复<br>循环结束]
    B —> G[流式事件输出<br>Thought/Action/Tool]
    G —> H[外部订阅<br>UI/日志/调试]
```
下面我们深入剖析这个循环的各个阶段、关键特性和设计哲学。
### 🔁 核心循环详解
Pi Agent 的核心循环在 `pi-agent-core` 包中实现，它剥离了所有终端 UI 和具体业务逻辑，是一个纯粹的、可嵌入的运行时。其核心循环的代码量非常精简，约 1,400 行，体现了“少即是多”的哲学。
| 阶段 | 核心动作 | 关键细节与特性 |
| :— | :— | :— |
| **1. 输入与上下文组装** | 接收用户消息或“转向”指令，组装完整的上下文（Context）。 | • **上下文管线**：分为两步<br>  1.  `transformContext()`: 在应用层裁剪或注入（如删除过旧消息）<br>  2.  `convertToLlm()`: 转换为 LLM 标准格式<br>• **树状会话**：会话历史以 `id` 和 `parentId` 构成树状结构，支持分支、恢复和探索<br>• **上下文压缩**：当历史过长接近上下文窗口限制时，自动进行压缩摘要，保留关键信息 |
| **2. 模型推理与决策** | 将组装好的上下文发送给 LLM，进行流式推理。 | • **模型无关**：通过 `pi-ai` 层统一了 30+ 家模型 API（OpenAI, Anthropic, Google 等），核心循环无需关心模型差异<br>• **双层消息格式**：内部统一使用 `AgentMessage`（应用层），仅在调用 LLM 的瞬间才转换为特定 Provider 的格式<br>• **流式事件**：输出 `thinking_delta`（推理）、`text_delta`（文本）、`toolcall_start/end`（工具调用）等标准事件，供外部订阅 |
| **3. 工具调用与执行** | 解析 LLM 输出中的工具调用意图，按序执行工具。 | • **原子工具**：默认仅内置 `Read`, `Write`, `Edit`, `Bash` 四个核心工具，覆盖了编程基础操作，极大减少了模型的认知负担<br>• **参数校验**：使用 TypeBox 为工具定义严格的参数 Schema，运行时自动校验<br>• **Steering 转向机制**：在工具执行过程中，允许用户发送新指令（“等等，改下方案”）。当前工具完成后，循环会**立即响应新指令**，调整后续计划，而非等待整个任务完成<br>• **Follow-up 追加机制**：允许用户在任务完成后追加新指令，循环会继续执行，类似排队 |
| **4. 结果注入与循环** | 将工具执行的结果（Observation）作为新的输入，注入上下文，然后**返回第2步**，开始下一轮推理。 | • **无限循环**：此循环会一直执行，**直到 LLM 自行声明任务完成**（输出 `end_turn` 或类似信号），没有固定的最大步数限制<br>• **事件驱动**：整个循环过程通过 `agent`, `turn`, `message`, `tool` 等级别的事件流对外广播，实现了极高的透明度和可调试性 |
### ⚙️ 核心循环的关键设计哲学
Pi Agent 的核心循环并非一个功能堆砌的“大而全”系统，其背后蕴含着清晰的设计哲学：
1.  **极简主义与控制权归还**：核心循环只做最必要的事（推理、调用、循环），**不内置** Plan Mode、To-do 系统、MCP 客户端或后台 Bash 等。它将**上下文构建的控制权、工具扩展的决策权**完全交还给开发者或上层应用（如 OpenClaw）。
2.  **“代码即真理”**：Pi 优先使用真实代码和文件操作来管理状态和记忆，而非维护一个独立的外部记忆系统。它通过代码注释和结构化摘要来管理对话历史，这使其更贴近真实开发者的工作流。
3.  **模型无关性**：通过 `pi-ai` 适配层，核心循环**不绑死任何一家模型**。开发者可以在会话过程中通过 `setModel()` 等 API **热插拔**模型，根据任务成本和复杂度动态切换。
4.  **透明与可观测**：核心循环的每一步（思考、决策、工具执行、结果）都通过事件流暴露。开发者可以订阅这些事件，构建自定义的 UI、日志系统或调试工具，解决了传统 Agent 的“黑盒”问题。
### 🧩 核心循环的扩展机制
Pi Agent 的核心循环本身保持极简，但它提供了强大的扩展点，让能力可以按需注入，而无需修改核心代码：
*   **Skills（技能）**：这是一个独立目录，包含一个 `SKILL.md` 文件说明“我是谁、什么时候用我”以及具体的能力定义。**核心循环会在需要时才动态读取并注入该 Skill 的说明和工具到上下文中**，任务完成后即释放，极大节省了 Token。Pi 甚至能自己生成 Skill。
*   **Extensions（扩展）**：TypeScript 编写的扩展，可以挂载到核心循环提供的**钩子系统**（如 `before_tool`, `after_tool`, `agent_start` 等）上，实现自定义逻辑，如注入动态上下文、拦截工具调用、审计日志等。
*   **Prompt 模板**：允许复用高频任务的提示词，进一步控制上下文。
### 📝 总结
Pi Agent 的核心循环是一个**遵循 ReAct 范式、事件驱动、无限循环**的执行引擎。它通过**极简的内核、模型无关的设计、强大的事件流和按需加载的扩展机制**，实现了高度的可控性、透明性和灵活性。它不是一个功能完备的成品，而是一个**为硬核开发者打造的、可控的 Agent 基础框架**，其价值在于将构建复杂 AI 应用的核心控制权交还给开发者，让开发者能精确控制输入模型的每一个 Token、每一个工具调用，从而构建出更稳定、更符合特定业务需求的智能体应用。
