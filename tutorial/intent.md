意图驱动编程实践指南


——

一、核心思想

代码是意图的沉降物，不是起点。

传统流程：想一下 → 写代码 → 代码变成唯一真相 → 意图丢失 → 维护爆炸

意图驱动流程：意图显式化 → 代码从意图推导 → 意图跟着代码走 → 任何时候都能从代码反推”为什么“


——

二、前置：什么是”意图“

意图不是需求文档，不是用户故事，不是PRD。意图是你作为开发者，在动手之前对自己说清楚的几件事：

层次	要回答的问题	例子
核心目标	这一坨东西本质上要干什么？一句话说清	”把用户的自然语言指令翻译成可执行的API调用序列“
边界	什么它不干？	”不负责鉴权、不负责重试、不处理并发“
约束	什么条件必须满足？	”延迟<200ms、必须可回滚、不能依赖外部状态“
已知假设	我基于什么前提在做事？	”假设输入已经过基础清洗、假设API不会返回部分结果“
不确定性	哪些地方我还没想清楚？	”错误恢复策略待定、批量场景的行为未定义“

最后一条最重要。把”不知道“显式写出来，比假装知道强一万倍。


——

三、正向流程：从意图到代码

Step 1：写意图声明（5-10分钟，别超过一页）

在动手写任何代码之前，先写下来。格式随意，但必须包含上面五层。

可以写在一个临时文件里、issue里、甚至prompt里。关键是写下来，不要只在脑子里转。

示例：

模块：query_planner
核心目标：把用户的模糊查询意图拆解成子查询的有向无环图
边界：不执行查询、不接触数据源、不做结果合并
约束：拆解结果必须可并行执行、每个子查询必须能独立失败
假设：用户输入已经过分词、查询图谱的schema已知且稳定
不确定：子查询之间的依赖关系怎么自动推断、循环依赖怎么处理


Step 2：把意图喂给模型，但要求它先输出推理链

不要直接说”帮我实现“。先让它把理解复述一遍：

基于上面的意图声明，告诉我：
1. 你理解的核心问题是什么？
2. 你打算怎么拆模块？
3. 你对每个”不确定“项的处理建议是什么？
4. 你做了哪些额外假设（我声明之外的）？


你只review推理链，不急着看代码。 如果推理链里有任何一步你觉得”不对“或”不是我想要的“——打回，不要继续。

Step 3：逐层生成，逐层确认

不要一次生成整个系统。按意图声明的模块边界，一次一个模块：

• 生成模块A → 你确认推理链 → 确认代码 → 锁定

• 生成模块B → 同上

• 模块A和B的接口对接 → 确认

每一步的”确认“不是”看起来能跑“，而是你能说清楚”这一步为什么是对的“。

Step 4：意图声明跟着代码走

最终落地时，意图声明放在模块入口文件顶部，作为注释或docstring：

”“”
INTENT:
  Core: 把用户模糊查询拆成子查询DAG
  Boundaries: 不执行、不合并、不碰数据源
  Constraints: 子查询可并行、可独立失败
  Assumptions: 输入已分词、schema已知
  Unresolved: 循环依赖处理策略待定
“”“

四、反向流程：从代码反推意图

当你面对一坨没有意图文件的代码时：

Step 1：宏观扫描，找”不自然“

快速浏览代码，标记所有让你觉得”为什么这样“的地方：

• 奇怪的数据结构选择

• 多余的抽象层

• 注释掉的代码块

• 看起来过度通用的接口

• 重复但略有不同的逻辑

这些不是”坏代码“，是意图偏移的化石。每个不自然的地方都对应一次”当时不知道该怎么做，先这么写了“。

Step 2：用git历史还原时间线

git log —oneline — <target_file_or_dir>
git log -p — <target_file>  # 看具体改了什么


关注：

• 早期commit：最接近原始意图

• 大块新增：可能是新意图注入

• 紧急fix：通常是意图跟现实冲突的信号

Step 3：让模型做”意图考古“

把代码喂给模型，用这个prompt：

这是一段没有文档的已有代码。请帮我：
1. 推测写这段代码时，作者的核心意图是什么
2. 标注哪些部分看起来是”核心逻辑“，哪些是后来追加的
3. 识别代码中的”犹豫痕迹“（注释掉的代码、过度防御、奇怪的边界处理）
4. 如果要从头写一份意图声明，你会怎么写？
5. 哪些地方看起来像是”写的时候不确定该怎么做“？

不要解释代码做了什么，我要的是设计意图的推测。


你拿到结果后做判断，不是全盘接受。 模型会过度合理化——它会给每个奇怪的地方编一个”合理“的解释。你要做的是：哪些推测说得通，哪些明显是模型在编。

Step 4：重建意图声明，验证

把反推出来的意图写成声明，然后问自己：

• 如果这个意图是真的，代码整体结构合理吗？

• 有没有跟意图矛盾的部分？（矛盾的部分就是偏移最严重的）

• 如果按这个意图重构，哪些可以删掉？

如果重构后代码变简单了——说明你的反推是对的。如果重构后反而更复杂——说明意图理解还有偏差。


——

五、意图偏移的早期检测

偏移不是一天发生的。它是每次”先这么写吧以后再改“积累出来的。检测信号：

信号	含义
你改一个bug，结果冒出两个新bug	代码已经不在原始意图的覆盖范围内了
你跟同事解释这段代码，越解释越复杂	意图已经被多层叠加污染
你让模型改一个地方，它改完别的地方坏了	模块边界已经模糊到模型都无法定位影响范围
你看着代码觉得”这谁写的“——然后发现是自己上周写的	意图丢失速度比你以为的快得多

出现任何一个，就该停下来做一次意图重建。


——

六、跟大模型协作的防偏移规则

1. 每次对话开头重申意图声明——不要假设模型记得。把它当成一个没有记忆的新人，每次都要把”我们要干什么、不干什么“说清楚。

2. 模型每输出一段代码，要求它标注”这一段的意图“——不是注释代码做什么，而是说”这一段是为了满足意图声明里的哪一条“。

3. 模型自己加的东西，必须显式标记——让它区分”你要求的“和”它自己觉得该加的“。你自己加的也要标记。每一行代码都应该能追溯到某个意图条目。

4. 不确定就停——如果模型拓展的方向你review的时候说不出”对，这是我要的“，那就别合并。宁可少一个feature，不要多一坨不知道为什么存在的代码。


——

七、最小可行实践（如果你不想搞这么重）

如果你觉得上面全套太重了，至少做这三件事：

1. 每个模块入口写5行意图声明（核心目标 + 边界 + 最大不确定项）

2. 让模型生成代码前先复述理解，你确认了再让它写

3. 每周花30分钟做一次”意图健康检查“——随便挑一个模块，看能不能在2分钟内说清它为什么存在、它不干什么

能做到这三件，你的情况会比现在好一大半。
